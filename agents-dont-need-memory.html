编者按

10 月 3 日，工程师 Kevin Liao 发表《Agents don’t need memory, they need documentation》，很快冲上 Hacker News 热榜，因为它精准戳中了当下 agent 工程最尴尬的痛点。主流做法执着于给 agent 装「长期记忆」（向量库、记忆压缩、遗忘曲线），但 Liao 指出，这条路是在模仿人脑，却忽略了软件真正擅长的东西： 可版本化、可检索、可审计的文档 。与其让模型「记住」上次做了什么，不如让它像工程师维护文档一样，把决策、约束、接口契约显式写下来，下次直接读。文档是外化的、可 diff、可回溯的记忆，而模型的隐式记忆则是黑箱、易漂移、难调试。

这个观点在实践层面很有共鸣：Claude Code、Cursor 这类工具真正拉开差距的往往不是「记忆多强」，而是能否围绕 README、AGENTS.md、issue 与 commit history 组织上下文。往深一层，它其实是在提醒整个 agent 行业：不要把「智能」浪漫化， 先把「工程可维护性」做扎实 ——会写、会读、会更新文档的 agent，比会「回忆」的 agent 更可靠。

“

让智能体去 记住过去 ，或许从一开始就是个伪命题——真正该做的，是让它学会 读文档、写文档 。

—— Kevin Liao

“记忆”插件 会分析你的对话记录，生成上千条彼此孤立的片段，把它们塞进一个 向量数据库 。你每发出一个提示（prompt），它就附上相似度最高的五条片段；要是智能体仍然一头雾水（它多半会的），还得自己去手动搜更多。 这就是他们所谓的“记忆” 。

可一旦你想清楚自己到底要解决什么问题，就会发现这东西用起来很别扭。你真正想要的，是让智能体 理解你的项目 ——知道某个功能在哪里、当初为什么这么建、你们敲定了什么、你在乎什么。可换来的却是一场 RAG 片段抽奖 ：每个提示都注入一批，祈祷碰巧有对的那几条浮上来。

即便它真的管用，智能体依然没有理解你的项目。整个“记忆插件”生态， 从一开始就在解决一个错误的问题 。

智能体不需要记忆，它们需要的是文档。

01

RAG

说到底，都只是 RAG

市面上的每一款记忆插件，运作方式都 一模一样 ：

1

翻一遍会话记录（transcript）

2

生成一条条“记忆”片段

3

插入一个 RAG 数据库

4

每次提示时，检索出 Top 5 并注入

5

还不够用？那就给智能体一个工具，让它自己在 RAG 数据库里搜

这就是全部的架构。有些工具花样更多：有的让智能体逐字检索过往的会话记录；有的搞出某种 多层级记忆系统 ，把记忆分成长期和短期；有的则塞进一大堆后台守护进程（daemon）来审阅、合并或去重记忆——那种在夜里重写记忆的“做梦者（Dreamers）”，还有持续的上下文压缩、重排序器（Reranker）等等，诸如此类。

每个插件都试图加上新的、 疯狂消耗 token 的“功能” ，去修补底下那套同样有缺陷的架构。也正因如此， 它们没有一个能可靠地工作 。


02

RECALL

“靠回忆”的问题

所有这些记忆插件，都困在几乎相同的一堆问题里。


记忆靠相似度浮现

相似度检索衡量的只是两条片段在嵌入空间里离得多近，仅此而已。你无法判断 哪条正确、哪条当前有效、又有什么被漏掉 。


记忆存储时脱离上下文

一个 RAG 片段装得下的东西有限，于是你丢掉了其余的一切： 上下文、动机、经验教训、运行环境 。


把过去当作事实

这些插件都依赖“回忆”，可 代码库每天都在变 。那么关于身份认证（authentication）的那 500 条片段，究竟还有多少是准确的？


智能体搜不出自己不知道的东西

就算你真的开了一个搜索工具，它又怎么知道该在什么时候用？ 智能体并不知道自己不知道什么 。


这个存储库无法审计

SQLite 里躺着上万个嵌入向量。到底存在哪些记忆？哪些已过期？哪些从来没被检索到过？ 哪些是错的、却在暗中影响智能体的行为 ？

而这些，只不过是记忆插件所面对、所尝试、却又修复失败的众多问题中的 五个 。因为它们都做出了同一个假设：

智能体会遗忘：这就是问题所在。所以解决办法就是“记住”。要想记得更好，就应该 抓取更多、索引更好、检索更聪明 。

它们的全部论点，都围绕“抓取并回忆过去”打转。可别人处理知识根本不是这么干的。没人为了记住某个功能的约束条件，去把三年前的团队会议录像重看一遍。人们的做法是 把它写下来，然后使用这些记录 。

同样地，解决办法不是给智能体一个搜索工具，让它在上千万 token 的历史对话里翻找，去拼凑出当时到底发生了什么的一鳞半爪。

“解决办法，是基于文档的记忆。”

如今，人们用 AI 以光速量产产品、功能和一堆注水的垃圾（slop），却连一行代码都不读、不懂。在这样的境况下很容易就能看出：文档为什么最终 沦落成了事后想起的东西 ——尽管此时此刻，它比以往任何时候都更重要。


03

DOCUMENTATION

用文档，替代回忆

人们早就知道智能体需要上下文，所以才发明了 AGENTS.md 文件：好让智能体不至于两眼一抹黑地扎进代码库。它确实管用。但很多时候，这一个文件就是整个项目 仅有的文档 。

单个文件是不够的。智能体需要的是一整颗“大脑”—— 一个结构化的工作区 ，让它能在无人吩咐的情况下自行记录指令、规格、决策、调研、索引等各种内容：规定代码评审流程该怎么走的指令、详述与用户讨论结论的规格文档、可复用的对某个陌生库或 API 的调研笔记。

当智能体干活时，它可以从这颗大脑里读取文件，获得 相关而完整的上下文 ；干完活后，它再更新那些过时的内容，在必要处补上新的文档——而在此期间，全局图景始终留在上下文里。记忆也就从一副硬绑在智能体身上的 RAG 数据库，变成了一个 你能读、能更新、甚至能分享的工作区 。

智能体循环的重构

— 从「提示 → 构建 → 遗忘」到「提示 → 查阅 → 构建 → 更新」


04

IN PRACTICE

拿到实战中检验

一年前，当我刚开始用 AI 编程时就意识到了这个问题。我想要一种让智能体 跨会话记住工作 的办法，于是先从创建一个 internal/ 文件夹入手——我要求智能体把一切都写下来：规格、计划、索引；并给它定下规矩：动手干活前，务必先读取相应的文档和索引，干完活后再更新它们。

这套起初相当粗糙的指令，慢慢演化成一套正式的系统，最终变成一个叫 Operator Memory 的插件。如今它已在我的每一个项目里被日常使用。

Operator Memory 用上文那套模型，提供了“基于文档的记忆”。它给你的智能体配了一颗 Markdown 大脑 ，让它把重要知识持久化下来：指令、规格、调研、索引。开工前，智能体总是先到这颗大脑里 查阅相关文档 ；收工后，智能体更新这颗大脑——重访那些陈旧的文档，在缺失之处补上新的文档。

没有向量数据库，没有嵌入向量，没有摘要器、整理器、更新器、“做梦者”，也没有任何其他疯狂消耗 token 的后台守护进程，更没有 黑盒式的检索 。

💡 用 Operator，一切都只是朴素的 Markdown 文档——你能读、能改、能提交（commit），还能分享给团队。

这套系统我已经用了一年多。想试试的话，它 免费且开源 ，地址： https://github.com/aerovato/operator-memory
